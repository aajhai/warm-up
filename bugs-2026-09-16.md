# Bugs from 16 Sep 2026 warmup

Four GoLogin profiles in **Available Profiles** (Aditi Jain, Kunal Mittal, banwari, Antonio Diaz). Production `once` with likes and connections enabled. Sequential. `--outside-hours` because four sessions would miss the 17:00 IST cutoff.

This is what actually broke. Not a backlog of every historical Orbita quirk.

---

## 1. Cloud connect probed a local Orbita debugger URL

**Severity:** blocker  
**Status:** patched in `src/browser/session.js` (uncommitted)

`connectWs()` always called `waitForDebuggerHttp()`, which rewrites the websocket to `http://…/json/version`. That is correct for `ws://127.0.0.1`. It is wrong for GoLogin Cloud:

`wss://cloudbrowser.gologin.com/connect?token=…&profile=…`  
→ `http://cloudbrowser.gologin.com/json/version?token=…`

Cloud start succeeded. The HTTP probe then failed with `fetch failed`. Error:

`Orbita debugger was not healthy before connect: fetch failed`

Hit: Aditi, Kunal, banwari (~54s each). Antonio was killed mid-start.

Patch: only run the HTTP health check when the endpoint is loopback `ws:`.

## 2. Infrastructure failures consume the production abort budget

**Severity:** high  
**Status:** open

Two aborted **production** sessions block the profile for the rest of the IST day. Connect-bug failures were counted as those aborts.

| Profile | After the first batch | After Aditi’s second run |
|---|---|---|
| Aditi | 1 abort | **2 aborts → blocked today** |
| Kunal | 1 abort | 1 left |
| banwari | 1 abort | 1 left |
| Antonio | unfinished `currentRun` (will become an abort on recover) | — |

Aditi then had a real feed session that still failed (bug 4). That second abort locked her out. A debugger-probe failure is not a LinkedIn challenge. Treating it like one burns the day’s capacity.

## 3. Crash postflight records `postsSeen: 0` / `expanded: 0`

**Severity:** medium  
**Status:** open

`runner.js` catch path:

```js
optimizer.postflight({ … postsSeen: 0, expanded: 0, aborted: true, reason: error.message })
```

Aditi’s logs showed posts in the DOM, scrolls, and three More expands. Saved state still says `postsSeen: 0`, `likes: 0`. Slack and `lastSession` therefore lie about whether the account did anything.

## 4. Cloud CDP dies: `Runtime.callFunctionOn` timeout, then `Target closed`

**Severity:** high  
**Status:** open

Aditi (second run): logged in, feed visible, ~15 min of browsing, then:

1. `11:15:48` Scroll gesture failed — `Runtime.callFunctionOn timed out`
2. `11:15:48` Wind-down started
3. `11:17:48` Wind-down gesture failed — same timeout
4. **~16 minutes of silence**
5. `11:33:23` `Protocol error (Runtime.callFunctionOn): Target closed`

`protocolTimeout` is 120s. Pointer commands have a 3.5s abandon path; `page.evaluate` / `Runtime.callFunctionOn` used by scroll-offset, feed inspect, and My Network does not. Once that channel wedges, the session sits on Puppeteer’s full timeout instead of bailing.

This matches the README’s unverified warning: Orbita CDP hangs are not solved for unattended cloud runs.

---

## 5. Session deadline and “stall” heartbeat do not stop a hung CDP call

**Severity:** high  
**Status:** open

Aditi’s plan was 14.1 min + 7 min grace ≈ **21 min**. The process lived **32.7 min**.

`runner.js` ticks every second:

- Deadline: `controller.abort("Session exceeded its execution deadline")`
- Stall: abort if `now - lastHeartbeat > 60_000`

Two defects:

1. The same interval **always** sets `lastHeartbeat = now`, so the stall check cannot fire unless the timer itself is starved.
2. `AbortController` is only observed at a few `throwIfAborted()` sites. An in-flight `Runtime.callFunctionOn` ignores abort until Puppeteer returns.

Deadline abort is documentation, not a kill switch.

---

## 6. Wind-down failure is not an abort; connection batch still runs

**Severity:** high  
**Status:** open

`linkedinFeed.js` logs wind-down failure and continues. `result.aborted` stays false. `runner.js` then starts `runConnectionBatch()`, which `page.goto`s My Network and runs several `page.evaluate`s.

That is the best explanation for Aditi’s 16-minute gap after wind-down: feed CDP was already dead, connections still tried, each evaluate could block up to 120s, then the target closed. No connection logs appeared; the error was thrown from the catch path with zero recorded connections.

A dead tab should not enter My Network.

## 7. “See new posts” recovery fires when the pill was never clicked

**Severity:** medium  
**Status:** open

Log pattern, both Aditi and Kunal:

```
See new posts did not jump the feed. Reloading /feed/.  { "clicked": false }
Skipping another /feed/ reload; reversing instead.     { "clicked": false }  × many
```

`refreshStaleFeed()` treats “stuck” (no new unique post URNs) or near-bottom as a stale feed. If `maybeSeeNewPosts()` returns false (`clicked: false` — no pill, or click missed), it still does a hard `/feed/` reload on the first pass. After that it `scrollTo(0)` in a loop.

The code already comments that repeated `goto(/feed/)` hangs Orbita CDP. Aditi’s first reload was followed later by bug 4. Not proven causal; the recovery is still noisy and aggressive.

Stuck is “same distinct post count”, not “scroll did not move”. A short feed that you have already seen will look stuck forever and keep jumping to top.

## 8. Pointer scroll often reports `moved: 0` on cloud Orbita

**Severity:** medium  
**Status:** open

Aditi, not at bottom (`top` ~400–500, `maxTop` 4279):

```
Scroll did not move the feed.  { "moved": 0, "ticks": 20–72 }
```

Then bug 7’s recovery kicks in. Trackpad CDP is what we use for “human” scrolling. On this cloud session it frequently did not move `main#workspace`. Soft `page.evaluate(scrollTo)` in the reload-skip path did move the offset, so the page was not frozen — the pointer gesture was.

---

## 9. SIGKILL leaves cloud browser, lock, and `currentRun`

**Severity:** medium  
**Status:** open (manual cleanup done for Antonio)

Killing the Node batch:

- Left `data/locks/browser.json` owned by a dead pid (`npm run unlock -- --lock browser` required).
- Left Antonio with `currentRun` set. Next start will `recoverInterruptedRun()` and increment `aborted`.
- Left a live GoLogin Cloud session. Stop required `DELETE https://api.gologin.com/browser/{id}/web`. SIGKILL does not run `CloudProfileLauncher.stop()`.

The service is supposed to own start/stop. A crash does not.

## 10. Two profiles were not in the local registry

**Severity:** low (ops)  
**Status:** fixed for this run in `data/profiles.json`

`data/profiles.json` only had Kunal and Aditi. Antonio and banwari existed in GoLogin **Available Profiles** but were not enrolled, so `npm run once -- --profile` would have refused them until the registry was updated. The scheduler would also have ignored them.

## What this run did *not* show

- Zero likes on Aditi/Kunal is consistent with a 2–5% like rate on ~20 posts. Not filed as a bug.
- Connection send/confirm UI still unproven live; Aditi never got a clean batch, Kunal had not finished when this was written.

## Order to fix (if the goal is unattended multi-profile warmup)

1. Keep bug 1’s cloud-connect skip (already in the working tree).
2. Abort the session when CDP times out; do not start connections on a dead tab (bugs 4 + 6).
3. Make deadline abort actually interrupt or disconnect the browser (bug 5). Heartbeat must not write `lastHeartbeat` on the same tick that is supposed to detect a stall.
4. Stop counting connect/CDP/process kills toward the two-abort LinkedIn safety cap, or classify them as `infra` (bug 2). Persist real `postsSeen` on crash (bug 3).
5. Tighten stale-feed recovery: no `/feed/` reload when See new posts was not clicked; don’t `scrollTo(0)` in a loop because unique URNs stopped growing (bugs 7 + 8).
6. On process exit, always stop the cloud profile and drop the lock (bug 9).
